# Decisiones de Diseño - Etapa 02

Durante el modelado de datos, el equipo tomó las siguientes decisiones de diseño:

1. **Uso de supertipo PERSONA:** Se decidió abstraer los datos comunes de `CLIENTE` y `TECNICO` en una entidad general llamada `PERSONA` para evitar la redundancia de atributos como Nombre, Apellido, DNI y Mail.
2. **Claves Primarias Artificiales:** Se optó por utilizar IDs numéricos (ej. `ID_Empresa`, `ID_Equipo`) como claves primarias para todas las entidades, facilitando así la vinculación entre tablas mediante claves foráneas. Los identificadores naturales como `DNI` o `CUIT` se configuraron con la restricción de "Unique".
3. **Gestión de Comprobantes:** Se generalizó el concepto de facturación centralizando los datos en la entidad `COMPROBANTE`, la cual se relaciona de forma modular con las compras de productos y las órdenes de reparación de equipos.
4. **Normalización mediante Tablas de Detalle**: Se implementaron entidades intermedias (`DETALLE_COMPRA`, `DETALLE_FACTURA`, `DETALLE_REPARACION` y `DETALLE_PAGO`) para resolver las relaciones de muchos a muchos del modelo. Esta decisión estructural permite almacenar los "atributos transaccionales" en el momento exacto de la operación. De esta manera, se garantiza el registro de las cantidades (necesario para la automatización del control de stock) y se congela el precio histórico o subtotal de los productos e insumos, evitando que futuras actualizaciones en los catálogos alteren los registros financieros pasados.
5. **Flexibilidad de Registros Mixtos y Prevención de Nulos**: En las tablas de detalle que agrupan diferentes tipos de elementos (como `DETALLE_FACTURA`, que puede registrar la compra de un producto o de un insumo), se decidió implementar claves primarias artificiales o subrogadas (ej. ID_Detalle_Factura) en lugar de claves primarias compuestas por sus entidades foráneas. Esto flexibiliza el registro, permitiendo ingresar renglones independientes para productos o insumos sin violar las restricciones de nulidad (NULL) inherentes a las claves primarias en las bases de datos relacionales.
6. **Desacoplamiento de Pagos**: Se separó el catálogo de `METODO_PAGO` de la transacción directa, vinculándolos mediante `DETALLE_PAGO`. Esta decisión responde a la necesidad de permitir pagos fraccionados, posibilitando que un mismo comprobante sea abonado combinando múltiples métodos (ej. efectivo y tarjeta) registrando el monto exacto de cada uno.
